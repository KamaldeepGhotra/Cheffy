## 1. What the MVP is

**Goal, in the owner's words:** as automated as possible, minimal button pressing. The only core features: add inventory, pick recommended meals or search meals, add them to the meal plan.

**Working version means:** both roommates open one hosted URL against one shared database. The Inventory tab takes `2 lb chicken, 12 eggs, cilantro` in one submit. The Recipes tab opens already ranked by what is on hand and each card has one tap, "Add to this week", that lands on the plan with sensible defaults. The Grocery tab shows this week's list without being asked, and one tap per line moves a purchase into inventory. Underneath, Gemini's ingredient names actually match inventory rows, units net out, and grocery math is per serving, so the derived lists are right instead of decorative.

**The weekly happy path after this plan** (taps, not counting typing):

1. Open the app. Recipes tab loads ranked by on-hand match. If the library is empty it asks Gemini for suggestions itself. **0 taps.**
2. Tap "Add to this week" on a card. Lands on today (or the next free day), assigned to you, 1 serving. **1 tap per meal.** Optional: type a dish name and press Enter to search a specific one, then the same 1 tap.
3. Grocery tab. This week's need / have list is already there, per serving, unit-normalized. **0 taps.**
4. Shop. Tap "Bought" per line or "Bought everything". Each line becomes an inventory row, merged into an existing row if there is one. **1 tap.**
5. Unpack extras: type `2 lb chicken breast, 12 eggs, 1 bunch cilantro`, Enter. **1 submit for N items.**
6. Meal Plan tab only to adjust: tap the person to cycle, +/− servings, × to drop. **1 tap each, optional.**

Today the same week is roughly eleven taps plus re-typing every purchased item.

**Explicitly cut from the MVP** (each is a separate feature afterwards):

- "Cooked it" subtracting ingredients from inventory. Unit mismatches would make it silently wrong until units are solid; revisit after K4 has been used for a week.
- Auto-filling the week (rotation, optimization). Spec says out of scope.
- Quantity-aware matching ("do we have *enough*"). Presence-only ranking is good enough to order the list.
- Real login. The "Who are you?" picker (A4) is the seam where Supabase auth plugs in later.
- Recipe detail page with step-by-step view. Cards show instructions collapsed; a dedicated view comes after.
- Unit conversion (cups to grams). Aggregation keys on normalized unit; mixed units stay as separate lines.
- Shared recent-add chips, recipe editing, push notifications, barcode scanning.

```python
UNIT_VOCABULARY: list[str]              # the canonical keys, for the Gemini prompt

def normalize_unit(raw: str | None) -> str:
    # 'cups' -> 'cup', 'Cloves' -> 'clove', 'lbs' -> 'lb', '' or None -> 'each'
    # unknown -> raw.strip().lower()   (NOT 'each': Gemini says 'leaves', 'pinch'; keep them visible)
```

Deliberately differs from the frontend, where an unknown unit becomes `each` with a warning. The backend keeps unknown units as typed so they can be seen and added to the table.

### 3.2 `backend/app/matching.py` (Andreas, A3)

```python
def normalize_ingredient_name(raw: str) -> str
```

Rules, in order: lowercase; cut at the first `,`, `(`, ` - `, or ` or `; drop tokens in a fixed stoplist; collapse whitespace; singularize the **last word only** with an exception list.

- **Stoplist:** prep participles and size words. `diced minced chopped sliced cubed shredded grated crushed peeled beaten melted softened thawed boneless skinless trimmed halved quartered drained rinsed cooked cold warm raw ripe large medium small extra-large`.
- **Not in the stoplist, on purpose:** `fresh dried frozen canned ground whole white brown`. Those change what you buy (fresh vs dried basil, ground beef vs beef). `cooked` **is** stripped because cooked rice is made from the rice you have.
- **Singularize:** `ies`→`y`, `oes`→`o`, trailing `s`→drop. Skip words ending in `ss` or `us` and the exception list `hummus asparagus couscous molasses`.
- Existing signatures of `find_ingredient_matches` and `resolve_or_create_ingredient` are **unchanged**; `_normalize` calls `normalize_ingredient_name` so both lookup and stored names go through it. Threshold stays 90.
- `resolve_or_create_ingredient` raises `ValueError` when the name normalizes to nothing (blank, or only punctuation such as `(`), so a blank ingredient row can never be stored. K3 treats that like a malformed Gemini ingredient.
- Measured on main today: `chicken breast` vs `boneless skinless chicken breast, diced` scores 52.8, `garlic` vs `garlic, minced` scores 60.0. After normalization both are 100.

Kam's `_persist_recipe` (K3) calls `resolve_or_create_ingredient(db, raw["name"])` exactly as today. No change on his side.

### 3.3 Gemini recipe dict v2 (Kam, K2)

Both `get_recipe_info(query) -> dict` and `suggest_recipes(ingredient_names: list[str], count: int = 3) -> list[dict]` return dicts of this shape, JSON mode:

```json
{
  "name": "Chicken Fried Rice",
  "servings": 4,
  "instructions": "1. ... 2. ...",
  "ingredients": [
    {"name": "chicken breast", "prep": "diced", "quantity": 1, "unit": "lb"}
  ],
  "calories": 430, "protein": 32, "fat": 13, "carbs": 45
}
```

- `name` in each ingredient is the **base ingredient only**; prep words go in `prep` (may be empty). The prompt says so explicitly and lists `UNIT_VOCABULARY` as the only allowed units.
- `quantity` is for the **whole recipe**, i.e. all `servings` portions. Nutrition is per serving. The prompt states both.
- `servings` is clamped to 1–12 on save; missing → `DEFAULT_RECIPE_SERVINGS`.
- `suggest_recipes([])` (empty inventory) uses different wording: "suggest simple, popular dishes" rather than an empty on-hand list.
- `class GeminiError(Exception)` is raised on any API failure or when the JSON does not have this shape. Nothing else escapes.

### 3.4 Recipes API (Kam, K3)

```
POST /recipes/search   {query}                      -> 201 RecipeOut            502 {"detail": "Recipe service unavailable, try again"}
POST /recipes/suggest  {household_id, count=3}      -> 201 list[RankedRecipeOut] 502 same
GET  /recipes?household_id=roommates                -> 200 list[RankedRecipeOut]  sorted match_percentage desc, then id desc
```

```python
class RecipeOut(BaseModel):        # existing, plus:
    servings: int

class RankedRecipeOut(RecipeOut):
    match_percentage: float        # 0-100, presence-only
    missing_ingredients: list[str]  # names, for "missing: garlic, cream" on the card
```

- `GET /recipes` **extends the existing `list_recipes`** at the bottom of `routers/recipes.py`. Do not add a second route. Without `household_id` it returns `match_percentage=0` and all ingredients missing.
- Suggest de-duplicates by `normalize_ingredient_name(name)` against the existing library and returns only the new ones.
- Both search and suggest go through one `_persist_recipe(db, info) -> Recipe` helper; units are stored via `normalize_unit`.

### 3.5 Ranking (Kam, K1)

```python
# backend/app/recipe_ranking.py
def compute_match(recipe: Recipe, on_hand_ingredient_ids: set[int]) -> tuple[float, list[str]]
```

Pure function, no DB access. The router loads the household's on-hand ingredient id set once and calls this per recipe. A recipe with no ingredients returns `(0.0, [])`.

### 3.6 Grocery API (Kam, K4)

```
POST /grocery-list  {household_id, recipe_ids, servings{recipe_id: n}}   -> unchanged response shape
GET  /grocery-list?household_id=roommates&week_start=2026-09-14           -> same response, derived from meal_plan_entries
```

- Math: `needed = ri.quantity * requested_servings / recipe.servings`. `servings` in the request now means **portions to eat**, which is what `MealPlanPage` already sends. Its existing button becomes correct with zero frontend edits.
- Aggregation keys on `(ingredient_id, normalize_unit(unit))` for both recipe lines and inventory rows.
- `GroceryLine` gains `ingredient_id: int` and `ingredient_name` stays. Needed so "Bought" can post the right thing.
- Both routes share one `_build_list(db, household_id, servings_by_recipe)` helper.

### 3.7 Inventory API (Andreas, A2)

```
POST /inventory  {household_id, ingredient_name, quantity, unit}
```

Unit is normalized server-side before matching or storing.
