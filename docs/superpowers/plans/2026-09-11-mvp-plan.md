## 1. The core model: this week's meals

Everything in the app hangs off one idea. A **meal** is a recipe you intend to cook this week, and it is in one of two states:

| State | What it means | In the data |
|---|---|---|
| **Planned** | You picked it. No day yet. | `meal_plan_entries` row with `day = NULL` |
| **Scheduled** | It has a day, a person, and a serving count. | `meal_plan_entries` row with `day = 0..6` |

That is the whole model. There is no separate "cart", "selection", or "shortlist" table.

Why this matters, concretely:

- **Picking a recipe** on the Recipes tab creates a planned meal. One tap.
- **Scheduling it** is filling in the day. The Meal Plan tab shows planned meals in a tray at the top; tapping a day drops one onto it.
- **The grocery list** is everything you're cooking this week — planned *and* scheduled. One source, no double-counting, nothing to press "generate" on.
- **Nothing is orphaned.** A recipe you picked but never scheduled still appears on the grocery list, because you still said you were cooking it.

The problem this fixes is structural, not cosmetic: today each tab derives its own state from scratch and none of them agree.

## 2. What the MVP is

**Goal, in the owner's words:** as automated as possible, minimal button pressing. The core features: add inventory, pick recommended meals or search meals, add them to the meal plan.

**Working version means:** both roommates open one hosted URL against one shared database. Inventory takes `2 lb chicken, 12 eggs, cilantro` in one submit. The Recipes tab opens already ranked by what's on hand, so a 90%-match chicken alfredo sits above a 50%-match stir fry, each showing exactly what's missing. Searching gives three options, not one, because the first suggestion isn't always the one you want. The Grocery tab is a checklist that's already filled in and already excludes what you have. The Meal Plan tab is where picked meals get days and owners.

**The weekly happy path** (taps, not counting typing):

1. Open the app on the Recipes tab. It's already ranked by what's in your inventory. If the library is empty it asks Gemini itself, using your on-hand items. **0 taps.**
2. Tap **Plan this week** on the cards you like. **1 tap per meal.** Or type a dish name, get three options with match percentages, tap the one you want. **2 taps.**
3. Grocery tab. The list is already there — need vs. have, per serving, unit-normalized, each line noting which meal wants it. **0 taps.**
4. Shop. Tap a line to check it off; it lands in inventory and moves to "Already have." **1 tap per line.**
5. Unpack extras: type `2 lb chicken breast, 12 eggs, 1 bunch cilantro`, Enter. **1 submit for N items.**
6. Meal Plan tab: planned meals sit in a tray; tap a day to schedule one. Adjust person and servings inline. **1 tap each.**

**Explicitly cut from the MVP** (each is a separate feature afterwards):

- "Cooked it" subtracting ingredients from inventory. Unit mismatches would make it silently wrong; revisit once units have been in real use for a week.
- Auto-filling the week (rotation, optimization). Spec says out of scope.
- Quantity-aware matching ("do we have *enough*"). Presence-only ranking is good enough to order a list.
- Real login. The "Who are you?" picker (P5) is the seam where Supabase auth plugs in later.
- Unit conversion (cups to grams). Aggregation keys on normalized unit; mixed units stay separate lines.
- Recipe editing, shared recent-add chips, push notifications, barcode scanning.

## 3. Design system and UX standards

**This section is binding on every task.** The biggest reason the app currently feels broken is not missing features — it's that failures and waits are invisible. Every "nothing happens when I click" report so far traced back to a silently rejected promise.

### 3.1 The three states rule

**Every view that loads data must handle all three states, and every mutating action must acknowledge itself.** A task is not done if any of these are missing:

| State | Requirement |
|---|---|
| **Loading** | A skeleton or "Loading…" line. Never an empty container. |
| **Empty** | A sentence naming what's missing and the action that fixes it — "No recipes yet. Tap *Get ideas* and we'll suggest some from your inventory." Never a bare empty list. |
| **Error** | The message from the thrown `Error` plus a **Retry** button. Never a silent console log. |
| **In-flight action** | The button disables and changes label (`Plan this week` → `Planning…`), or the row updates optimistically. Never a dead-looking button. |

`api.js`'s `request()` already throws `Error(detail)` on non-2xx. Catch it and put it on screen.

### 3.2 Visual system

Owned by P1, which lands before any other UI task. All tokens live in `frontend/src/index.css` as custom properties on `:root`, with a `prefers-color-scheme: dark` block.

- **Mobile-first.** Single column, `max-width: 560px`, centered, 16px gutters. Both roommates use this on phones.
- **Spacing scale:** `--space-1: 4px` through `--space-6: 32px`. No arbitrary pixel values in page CSS.
- **Type scale:** `--text-sm: 13px`, `--text-base: 15px`, `--text-lg: 18px`, `--text-xl: 22px`. Body is `--text-base`.
- **Color tokens:** `--bg`, `--surface`, `--border`, `--text`, `--text-muted`, `--accent`, `--accent-text`, `--success`, `--danger`. Both themes defined. Nothing hardcodes a color outside `index.css`.
- **Radius:** `--radius: 10px`, `--radius-sm: 6px`.
- **Tap targets:** minimum 44px tall for anything tappable.
- **Component classes** (defined in `index.css`, used by both people's pages): `.card`, `.btn` with `.btn-primary` / `.btn-secondary` / `.btn-ghost`, `.chip`, `.row` (flex list row with a trailing action), `.badge`, `.skeleton`, `.banner-error`, `.empty`.
- **Page-specific CSS** goes in `pages/<name>.css`, imported by that page. Only P1 edits `index.css`.

### 3.3 Match percentage display

Consistent everywhere a recipe appears:

- A `.badge` with the integer percent: `90%`.
- Colored by band: ≥80% uses `--success`, 40–79% uses `--text`, <40% uses `--text-muted`. High-match recipes should be visibly the point of the screen.
- Directly beneath, when anything is missing: `Missing: garlic, heavy cream` in `--text-muted` at `--text-sm`. Three names maximum, then `+2 more`.

## 5. Contracts

### 5.1 Already on main, unchanged

`backend/app/units.py` — `CANONICAL_UNITS`, `UNIT_VOCABULARY`, `normalize_unit(raw) -> str` (unknown units pass through as typed, not coerced to `each`).

`backend/app/matching.py` — `normalize_ingredient_name(raw) -> str`, `find_ingredient_matches(db, name, limit) -> list[tuple[Ingredient, float]]`, `resolve_or_create_ingredient(db, name, ...) -> Ingredient`. Threshold 90. **`resolve_or_create_ingredient` raises `ValueError` when the name normalizes to nothing** (blank, or punctuation only) so a blank ingredient row can never be stored — `_persist_recipe` must treat that like any other malformed Gemini ingredient and surface it as `GeminiError` → 502 rather than letting a `ValueError` escape as a 500.

`backend/app/recipe_ranking.py` — `compute_match(recipe, on_hand_ingredient_ids: set[int]) -> tuple[float, list[str]]`. Pure, no DB access. Returns `(percentage, missing_names_in_recipe_order)`; a recipe with no ingredients returns `(0.0, [])`.

`backend/app/gemini_client.py` — `GeminiError`; `get_recipe_info(query) -> dict`; `suggest_recipes(ingredient_names, count=3) -> list[dict]`. Both return the v2 dict shape below and raise `GeminiError` on API failure or bad shape.

**Gemini recipe dict v2:**

```json
{
  "name": "Chicken Fried Rice",
  "servings": 4,
  "instructions": "1. ... 2. ...",
  "ingredients": [
    {"name": "chicken breast", "prep": "diced", "quantity": 1, "unit": "lb"}
  ],
  "calories": 430, "protein": 32, "fat": 13, "carbs": 45
}
```

Ingredient `name` is the base ingredient only; prep words go in `prep`. `quantity` covers the whole recipe (all `servings`). Nutrition is per serving. `servings` is clamped to 1–12 on save; missing → `DEFAULT_RECIPE_SERVINGS`.

### 5.2 Meal plan (Andreas, P2)

`MealPlanEntry.day` and `.assigned_to` become **nullable**. `day = NULL` means planned-but-not-scheduled.

```
GET    /meal-plan?household_id=&week_start=   -> 200 list[MealPlanEntryOut]
         ordered: planned first (day IS NULL), then by day, then id
POST   /meal-plan  {household_id, week_start, recipe_id, day=null, servings=1, assigned_to=null}
         -> 201 MealPlanEntryOut          404 unknown recipe_id
PATCH  /meal-plan/{id}  {day?: 0-6|null, servings?: int>=1, assigned_to?: str|null}
         -> 200 MealPlanEntryOut          422 empty body (model_validator)   404 unknown id
DELETE /meal-plan/{id}                     -> 204
```

```python
class MealPlanEntryOut(BaseModel):
    id: int
    week_start: date
    day: int | None            # None = planned, not scheduled
    recipe_id: int
    recipe_name: str
    servings: int
    assigned_to: str | None    # None = nobody claimed it yet
```

`PATCH` with an explicit `day: null` moves a scheduled meal back to planned. Use Pydantic's `model_fields_set` to distinguish "field absent" from "field set to null" — absent means leave alone, null means clear.

### 5.3 Recipes (Kam, R1 and R2)

```
GET  /recipes?household_id=                      -> 200 list[RankedRecipeOut]
       sorted by match_percentage desc, then id desc
POST /recipes/suggest  {household_id, count=3}   -> 201 list[RankedRecipeOut]   502 on GeminiError
POST /recipes/search   {household_id, query, count=3}
                                                 -> 200 list[RecipeCandidate]   502 on GeminiError
POST /recipes          {household_id, candidate} -> 201 RankedRecipeOut
```

```python
class RecipeOut(BaseModel):          # existing, plus:
    servings: int

class RankedRecipeOut(RecipeOut):
    match_percentage: float          # 0-100, presence-only
    missing_ingredients: list[str]   # names, in recipe order

class RecipeCandidate(BaseModel):    # a search result; NOT saved yet
    name: str
    servings: int
    instructions: str
    ingredients: list[CandidateIngredient]   # {name, prep, quantity, unit}
    calories: float | None
    protein: float | None
    fat: float | None
    carbs: float | None
    match_percentage: float
    missing_ingredients: list[str]
```

- **Search does not save.** It returns `count` candidates scored against inventory without writing anything. The user picks one, the client posts it back to `POST /recipes`, and only that one persists. This is what keeps the library free of rejected results.
- Scoring an unsaved candidate needs a read-only lookup, added to `recipe_ranking.py` (Kam's file), calling the existing `find_ingredient_matches` — **it must not create ingredients**:

```python
    # ingredient id is in on_hand counts as had. Everything else is missing. Never writes.
```

- `GET /recipes` **extends the existing `list_recipes`** at the bottom of `routers/recipes.py`. Do not add a second route. Without `household_id`, return `match_percentage=0` and everything missing.
- `POST /recipes/suggest` de-duplicates against the library by `normalize_ingredient_name(name)` and returns only what's new.

### 5.4 Grocery (Kam, R3)

```
GET  /grocery-list?household_id=&week_start=              -> 200 GroceryListResponse
POST /grocery-list  {household_id, recipe_ids, servings}  -> unchanged, kept for tests and direct callers
```

```python
class GroceryLine(BaseModel):
    ingredient_id: int
    ingredient_name: str
    needed: float
    unit: str
    recipes: list[str]      # meal names wanting this line, for "for Chicken Alfredo"

class GroceryListResponse(BaseModel):
    need: list[GroceryLine]
    have: list[GroceryLine]
```

- The `GET` derives from **every** `meal_plan_entries` row for that household and week — planned and scheduled alike. This is what makes the tab prefill itself.
- Math: `needed = ri.quantity * entry.servings / recipe.servings`. Aggregation keys on `(ingredient_id, normalize_unit(unit))` for both recipe lines and inventory rows.
- Both routes share one `_build_list(db, household_id, servings_by_recipe)` helper.
- Marking a line bought is just `POST /inventory` from the client with `{ingredient_name, quantity: needed, unit}`. No new endpoint.

## 8. Working rules

- **State who you are** to your Claude session first. It must not edit the other person's files. If it wants to, stop and ask in chat.
- **One task, one branch, one PR.** Merge `main` into your branch before opening it.
- **§3.1 is not optional.** A page with no empty state, no error state, or a button that gives no feedback is not done, however well the happy path works.
- **Contract change:** say so in chat, update §5 in the same PR.
- **After P2 and R1 land, delete `backend/cheffy.db`.** `create_all` does not alter existing tables — a stale file gives confusing `OperationalError`s about missing columns.
- **No AI-authorship attribution** anywhere in the repo: commits, comments, README, PR text.
- **Tests for real logic** (parsers, normalizers, math, ranking, endpoints). Plain UI wiring is verified in a browser before the PR — actually click through it, including one deliberate failure, to confirm the error state renders.
- **`uvicorn --reload` has been unreliable in this project.** If a change doesn't seem to take effect, fully stop and restart the server before debugging anything else.
